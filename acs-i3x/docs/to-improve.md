# i3X Service — To-Improve Document (TID)

Tracked deviations from the i3X spec and known areas for improvement.

## Spec Deviations

| ID | Area | Deviation                                                | Reason                                                                                    | Resolution path                                              | Status |
|----|------|----------------------------------------------------------|-------------------------------------------------------------------------------------------|--------------------------------------------------------------|--------|
| D1 | Auth | Using HTTP Basic Auth instead of API keys (MUST in spec) | PoC simplicity — Basic Auth maps directly to Factory+ username/password via ServiceClient | Implement API key / Bearer token auth with principal mapping | Open   |
| D2 | Response Format | Error envelope omits `error.code`. Spec requires `{ success: false, error: { code, message } }`; implementation returns only `{ message }` (`lib/middleware/envelope.ts:39`) | HTTP status is set correctly but never mirrored into the body. Overlooked when the error handler was first written | Add `code: status` alongside `message` in the error JSON body | Resolved |
| D3 | Subscriptions | `POST /subscriptions/delete` returns `{ deleted: [...] }` (`api-v1.ts:427`). Spec requires bulk-results envelope: `{ success, results: [{ success, subscriptionId, result: null }] }` | PoC shortcut — flat array felt simpler than per-id results | Build per-id results in the handler, returning success/error per subscriptionId | Resolved |
| D4 | Subscriptions | `POST /subscriptions/register` returns `{ registered: [...] }` (`api-v1.ts:435`) and aborts on first bad elementId. Spec requires bulk-results envelope **and** "Server MUST support partial failures (e.g. bad elementId) and not fail the full request" | PoC shortcut; partial-failure handling not yet implemented | Iterate elementIds, collect per-id success/error, return bulk envelope | Resolved |
| D5 | Subscriptions | `POST /subscriptions/unregister` returns `{ unregistered: [...] }` (`api-v1.ts:444`); same partial-failure gap as D4 | As D4 | As D4 | Resolved |
| D6 | Subscriptions | `POST /subscriptions/list` returns a flat array of `{ clientId, subscriptionId, displayName }` (`subscriptions.ts:67–80`); spec requires bulk envelope AND a `monitoredObjects: [{ elementId, maxDepth }]` field per subscription | Registered-element detail isn't currently exposed by `SubscriptionManager` | Track per-element maxDepth in the subscription state, expose it from `list`, wrap response in bulk envelope | Resolved |
| D7 | Subscriptions | Deleted / non-existent subscription returns HTTP 500. Spec: "Subsequent calls to `/sync` or `/stream` for a deleted or non-existent Subscription MUST return 404 Not Found." `clientId` mismatch should be 403 | `getAndVerify` (`subscriptions.ts:213–218`) throws a plain `Error` with no `.status`, so the error handler defaults to 500 | Throw an error with `.status = 404` for missing subscription and `.status = 403` for clientId mismatch (or use `APIError` from `@amrc-factoryplus/service-api`) | Resolved |
| D8 | Query / Subscriptions | No HTTP 206 path for partial `maxDepth` results. Spec: "If the server can return a partial result … it MUST return HTTP 206." | No server-imposed depth cap currently exists, so the partial-result path was never wired up. Latent deviation that will activate if a cap is introduced | Optional server cap via `I3X_MAX_DEPTH_CAP` env var (default `0` = unlimited). When set, `POST /objects/value` clamps requested `maxDepth` and returns HTTP 206; `/info` advertises `capabilities.query.maxDepthCap` | Resolved |

## Known Limitations to Improve

| ID | Area                        | Current behaviour                                                                              | Ideal behaviour                                                                                | Notes                                                                         | Status |
|----|-----------------------------|------------------------------------------------------------------------------------------------|------------------------------------------------------------------------------------------------|-------------------------------------------------------------------------------|--------|
| L1 | Device discovery            | Re-poll ConfigDB/Directory every 60s to detect new devices                                     | Use Directory's PostgreSQL LISTEN/NOTIFY or MQTT `Last_Changed/*` events for real-time updates | ConfigSync (`lib/sync.ts`): one WATCH of the Device class and one ConfigDB ETag SEARCH each for DeviceInformation, Info and Schema. Stored ETags are compared on every snapshot and only changed configs are fetched; each change is applied as one per-device mutation of the SQLite tree. UNS-discovered nodes preserved across config-driven updates. This replaced the per-config WATCH pipeline described in `docs/2026-05-14-incremental-object-tree-refresh.md`. Directory-side notify (online/offline state) still polled. | Resolved |
| L2 | ObjectTypes without schemas | Return empty `{"type": "object"}` schema for ConfigDB classes missing a ConfigSchema app entry | Either require schemas or synthesise from Sparkplug birth certificate structure                | Most real devices will have schemas; this is an edge case                     | Open   |
| L3 | SSE streaming scope | SSE subscriptions only stream values from devices publishing to UNS (requires UNS ingester + ISA-95 config) | Stream from all devices, including those only on Sparkplug | Could subscribe to `spBv1.0/#` directly, or use the historian's Sparkplug data. Needs design work — Sparkplug uses protobuf + aliases which requires birth certificate tracking | Open   |
| L4 | Device identity | Device elementId uses ConfigDB UUID, sub-objects use Instance_UUID. Ideally these would be consistent | Use Instance_UUID throughout, or provide a mapping endpoint | Too late to change for PoC without breaking the parent chain from ConfigDB | Open   |
| L5 | Memory at fleet scale | The tree, values, config bodies and RAG index lived on the JS heap (about 116 KB per device); 2N per-config WATCHes; an unbounded HTTP cache | Constant memory per process, whatever the fleet size | Tree and last values in SQLite (`lib/store.ts`), ConfigDB ETag searches, uncached fetches, RAG and MCP opt-in, streamed `GET /objects`, bounded subscription queues | Resolved |
| L6 | Values after a restart | Last values are cleared at start and on an MQTT reconnect, because UNS messages sent while i3X was not listening are lost. The first read of each metric after that goes to InfluxDB | Catch up from InfluxDB with one bulk `last()` over the gap, so reads stay local | Correctness first: serving a pre-restart value as current would be wrong | Open |
| L7 | Metrics with no InfluxDB data | A leaf with no value in the last 30 days is queried again on every read | Remember "no data" for a short time | Only matters for clients that poll whole fleets with many never-written metrics | Open |
| L8 | `Address` compositions | `METADATA_KEYS` skips any originMap key named `Address`, so such compositions only appear when UNS data arrives for them | Tell metadata keys from containers by their shape, not their name | Found in the October 2026 scale work; unchanged by it | Open |
