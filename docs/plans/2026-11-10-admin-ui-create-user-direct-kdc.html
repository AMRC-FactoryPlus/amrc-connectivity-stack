Create Users from the Admin UI — direct-to-KDC alternative

Companion to docs/plans/2026-11-09-admin-ui-create-user.md (left unmodified). Full text: docs/plans/2026-11-10-admin-ui-create-user-direct-kdc.md.

Why reconsider

The original plan creates users by submitting a KerberosKey CR for acs-krb-keys-operator to reconcile. That operator never raises kopf.PermanentError — every failure, even a permanent one, retries forever — so the calling service can't tell "slow" from "will never finish" and is forced into a bounded poll with a "still provisioning" UI state. This plan has the new service talk to the KDC directly via kadmin instead, trading a second kadmin-credential holder for a genuinely synchronous request.

Kadmin credential holdersOne — acs-krb-keys-operator onlyTwo — operator + new op1useradmin (explicit trade-off)

Kubernetes RBACNew Role: create/get/watch on kerberos-keys, Secret createNone — service only talks HTTP + KDC, no K8s API access
Password handlingBriefly written to a one-off K8s Secret for the operator to readStays in request body / process memory only, never persisted
Duplicate-principal failureSpins operator into infinite retry if not pre-checkedImmediate 409, same pre-flight check, no retry risk either way

Components

01lib/py-service-client (new shared lib)

  • Extracted from acs-krb-keys-operator's internal service_client/, mirrors lib/js-service-client's role
  • Adds new check_acl/fetch_acl to auth.py — the operator never needed ACL checks before
  • Both the operator and the new service depend on it via a local path dependency

02acs-user-admin (new pure-Python service)

  • Flask app, POST v1/user
  • lib/kadmin.py — the Kadm wrapper lifted near-verbatim from the operator
  • lib/auth.py — new inbound SPNEGO/Bearer auth, modeled on js-service-api's FplusHttpAuth

03New KDC identity + ACL scoping

  • Dedicated principal op1useradmin, not a reuse of op1krbkeys
  • kadmind ACL grants only ac (add principal, change password) — no delete/modify rights
  • Flagged as the main security-sensitive piece of this plan

04acs-service-setup bootstrap

  • Unchanged in shape from the original plan
  • ACS.Service.UserAdmin, UserAdmin.Perm.ManageUsers, granted to Administrator

05Helm deploy

  • Three containers, mirroring the operator's own Deployment: app + tgt-creds + kadmin-creds k5start sidecars
  • No ClusterRole/RBAC at all — simpler than the CR-based plan's Secret + CRD permissions

06lib/js-service-client + acs-admin UI

  • Same shape as the original plan: UserAdmin interface, CreateUserDialog.vue
  • UI drops the 202 "still provisioning" branch — only success/error toasts now

Risk callout

Trade-off accepted, not eliminated This plan deliberately gives up the original design's "only one thing holds kadmin credentials" property. The mitigations are a dedicated, least-privileged KDC principal (op1useradmin, ac only) and zero Kubernetes RBAC for the new service — but a second kadmin-capable credential and a second native python-kadmV build now exist in the cluster. Verify the restricted ACL line actually holds (step 4 of the plan's Verification section) before relying on it.
