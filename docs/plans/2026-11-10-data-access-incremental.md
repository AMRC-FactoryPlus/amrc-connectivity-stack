# Data Access: per-change dataset index, keyed notify views, and a maker that never queues stale work (revision 2)

Base path W = the repository root. DA = W/acs-data-access. I edited no repo file.

I checked every major finding of both reviews against the code. All six are correct, and this revision fixes each one. No review finding is wrong. I declined two minor suggestions and say why in the open questions.

The structure of the plan does not change. (1) DataFlow builds its maps per change from cdb.search_app_changes through pure reducers and re-resolves only the changed dataset and its transitive referrers. (2) All eight notify endpoints become projections of a per-subscription DatasetView that recomputes one body per changed key. (3) The default dataset maker runs one pass at a time from the latest inputs, makes 4 datasets at a time, and stamps each dataset when it is written. api-v1.js is not edited. No shared library changes.

What this revision changes:
- Notify readiness matches today's code (compat major 1). The metadata SEARCH waits only for the dataset map and the ACL. WATCH v2/metadata/:uuid waits for nothing and sends its bodyless 200 at once, including for a principal that Auth does not know. Verified at DA/lib/notify.js:106-144: every input has startWith(IMap()).
- The permission agreement test is split (compat major 2). APIv1.check_dataset_acl reads the raw UNS device config (DA/lib/api-v1.js:203-207, 219-232), so it allows an invalid default dataset through UseDevice and the lists do not. The plan pins that existing difference and changes neither side.
- No rxu.mapStartStops (cost major 1). W/lib/js-rx-util/lib/starts-stops.js:18-21 runs two Immutable subtract passes over the whole member set on every change. A small local operator, watch_each, replaces it for the structure apps and for parts. It diffs with native has() calls, reports added and removed members, and emits the set event before it subscribes a new member, so the merge-order trick of revision 1 is gone too. The whole-list delivery from ConfigDB stays O(N) per member change by wire contract; the plan names it as a residual and counts it.
- The burst proof holds every remaining O(N) path open (cost major 2): four lists and two single watches per session, and a fourth principal whose ACL grows by one target on every create.
- The maker cannot run two passes at once and cannot write after stop() (cost major 3). The copied coalesce errors its subscriber while a call still runs (W/acs-configdb/lib/rx-util.js:73), so the guard lives in the class.
- A single WATCH v2/metadata/:uuid opens one ConfigDB WATCH, not one per dataset (cost major 4). It uses a per-dataset parts source.
- Test specification fixes: the quadratic baseline is a ratio at two small sizes, three more baselines fail on today's code and flip later, goldens sort every order that was never specified, the shape catalogue is asserted as a subset, every step that makes a dataset invalid is in scenario B only, and every test waits with one settle() helper.
- SEARCH handoff is safe by construction: updates that arrive between the snapshot and the next macrotask are held in an array and sent in order, so nothing can queue behind the snapshot inside SearchFilter.with_full.

Seven stages. Stage 1 adds only tests and a scale harness against the unchanged code. Every stage leaves `npm test` green. Run the suite with Node 24, because vitest 4 does not start on the shell's default Node 18:
cd acs-data-access && npm test

One decision still needs your confirmation: whether SEARCH v2/structure/ lists invalid datasets (recommended, matches GET /v1/structure/:uuid and the Admin model) or leaves them out. The plan builds the recommended choice.

## Root causes

- CONFIRMED, dominant (measured by the map, code read by me): the two notify SEARCH handlers are quadratic. DA/lib/notify.js:306-328 (metadata_search) and 404-424 (structure_search) run a switchMap over the allowed UUID list and a combineLatest over one pipeline per dataset. Each per-dataset pipeline calls DataFlow.allowed_valid_datasets (DA/lib/dataflow.js:122-129), which is unshared and filters the whole map (dataflow.js:96-108). The UUID list has no distinctUntilChanged, so every dataset-map emission tears down and rebuilds all N pipelines. Measured by the map: 2.9 s of blocked event loop per dataset made per open Admin session at N=713, 6 to 9 s with two sessions, 9.5 to 17.8 s with three. With no session open the same change costs under 10 ms. This explains the 11 s per dataset and the 2 to 7 s requests.
- CONFIRMED: every SEARCH snapshot is followed by one duplicate child update per child. DA/lib/notify.js:222-225 starts the diff from an empty map (startWith(IMap()) then pairwise). Those N updates are emitted while SearchFilter.with_full (W/lib/js-service-api/lib/notify-v2.js:98-110) still awaits full(), so they queue in its concatMap. rxjs drains that queue recursively (mergeInternals calls doInnerSub from inside the previous inner's finalizer), so a long queue overflows the stack. The point where delivery stops depends on the Node version: the cost review's bare-pipeline probe delivered 372 of 400 on Node 18.20.8 and 1,038 of 2,000 on Node 24.13.0. Production runs Node 22, which nobody tested and which is not installed on this machine.
- CONFIRMED: SEARCH v2/structure/ never answers while the principal can see one invalid dataset. structure_search lists allowed_all_dataset_uuids (notify.js:399), but each child stream reads allowed_valid_datasets and filters out missing values (notify.js:368-374), so combineLatest never emits.
- CONFIRMED: the maker queues stale lists and remakes datasets. DA/lib/default-datasets.js:167-169 pipes jobs() through concatMap, which has an unbounded buffer. make_all stamps `made` with the pass start time (lines 187, 193), so after a pass longer than the 60 s settle every queued list remakes every dataset in it. The map's simulation with the real class gave 442 create_object calls for 40 devices; the stage 1 baseline site (40 devices, 500 ms per call) measures 414 on the old maker. The five ConfigDB calls of make() (lines 245-253) are awaited one after another on the blocked event loop.
- CONFIRMED but small: DataFlow rebuilds everything on any structure-app change. The grouped map (dataflow.js:309-335), the normalise pass (408-440), the resolve-all pass (682-723), valid_datasets (750-753) and default_devices with one SHA-1 per UNS device dataset (736-743) are all O(N). Measured 6 to 9 ms at N=713. It is not the cause of the seconds, but it is the O(N) the goal removes. default_devices emits a new Map on every datasets emission, so watch_allowed (dataflow.js:83-93) re-emits and every allowed_* subscription emits twice per change.
- CONFIRMED: `parts` (dataflow.js:217-240) holds one ConfigDB WATCH per dataset through cdb.watch_members_subclasses (W/lib/js-rx-client/lib/configdb.js:120-138), re-subscribes all of them on every Dataset member change, and emits nothing until all have answered. A cold GET /v1/metadata/:uuid (DA/lib/api-v1.js:475-477) and a single WATCH v2/metadata/:uuid (notify.js:129-136) each open N watches to answer for one dataset.
- CONFIRMED: any General information write on the site wakes every per-dataset metadata stream of every session (notify.js:114-117). Measured by the map: 209 ms per write per session.
- CONFIRMED: DataFlow is lazy. run() does nothing (dataflow.js:38-42) and rxu.shareLatest drops the upstream 1 s after the last subscriber leaves (W/lib/js-rx-util/lib/util.js:73). Only DefaultDatasets keeps `datasets` hot, and only on a site with a UNS bucket (DA/bin/api.js:127-132).
- CONFIRMED: one malformed stored config stops everything. A null Session limits config throws at dataflow.js:525 and a Union components config that is not an array throws at line 606. The throw errors the shared `datasets` stream for every route and every session.
- CONFIRMED: auth.watch_acl_with_perm (W/lib/js-rx-client/lib/auth.js:62-71) has no change check and is not shared per permission. Every ACL push for a principal filters the whole ACL and emits a new Set once per subscriber.
- CONFIRMED residual, by wire contract: every Dataset member change makes ConfigDB send the whole member list. cdb._watch_set (W/lib/js-rx-client/lib/configdb.js:44-49) parses it, builds an Immutable Set and compares it with the previous one. The cost review measured 0.35 ms at N=713 and 1.6 ms at N=4,000 for that part. rxu.mapStartStops (W/lib/js-rx-util/lib/starts-stops.js:13-22) would add 0.87 ms and 3.79 ms; this plan does not use it.
- NOT REPRODUCED: the exact path that put 'Could not load datasets from the Data Access service' on screen. The Admin store sets that text only when the metadata SEARCH errors or the store fails to start (W/acs-admin/src/store/useDatasetsStore.js:194-203, 229-234). A SEARCH errors at the client when the subscription gets a status of 300 or more (W/lib/js-rx-client/lib/notify-v2.js:186-187), which the server sends as 500 after any source or pipeline error (W/lib/js-service-api/lib/notify-v2.js:299-302). Two candidates: the stack overflow above, which rxjs catches and turns into subscriber.error in mergeInternals, and a source error during the burst. Neither was reproduced with the real Session pipeline. Stage 7 asserts the positive: no session receives a status of 400 or more during the burst.
- CORRECTIONS to the brief: the ConfigDB method is search_app_changes (configdb.js:199), not search_changes. It emits { map, child, previous }; child and previous are null on a snapshot or resync; a child delete of an absent key gives map === previous (W/lib/js-rx-client/lib/notify-v2.js:332-361). Cause (1) in the brief is true but costs milliseconds. Cause (3) costs the seconds; it needs an open Datasets page and is quadratic in datasets and linear in sessions.

## Design

LAYERS (bottom to top). New files use the canonical style (4 spaces, snake_case, header "ACS Data Access Service / purpose / Copyright 2026 University of Sheffield"). Edits to existing files keep the 2-space style of those files.

0. HELPERS. DA/lib/rx-util.js (new).
- coalesce(fn): copied from W/acs-configdb/lib/rx-util.js:41-83 with a comment that names the source. One call in flight; later triggers collapse into one further call.
- watch_each(factory, stats): an operator over a sequence of Sets (anything with has() and iteration; Immutable or native). It keeps a native Map key -> Subscription. For each new Set it finds the added keys (in the Set, not in the Map) and the removed keys (in the Map, not in the Set) with native has() calls, adds the Set size to stats.scanned when stats is given, emits { set, added, removed }, unsubscribes the removed keys, then subscribes factory(key) for each added key and emits { key, value } for every inner value. The set event is always emitted before the first value of a new key; this holds by construction for synchronous sources such as rx.of. An inner error errors the output. The output completes when the outer and every inner have completed, so fakes built on rx.of still complete. A key that stays in the Set is never re-subscribed.
- same_set(a, b) and set_changes(a, b) (the symmetric difference of two native Sets).

1. SOURCES. DA/lib/app-configs.js (pure, no rxjs).
- class AppMap: one per ConfigDB application. apply({ map, child, previous }) returns { map, changed } or null. It holds its own persistent Immutable Map. A child update compares the held value with map.get(child) by identity, then with json_equal from @amrc-factoryplus/service-api (W/lib/js-service-api/lib/util.js:63), and does one set or delete. The first snapshot gives changed: null. A later snapshot (reconnect, or after a parent error) is diffed against the held map in both directions: keys whose value differs are replaced, keys absent from the new snapshot are deleted, and unchanged bodies keep their object identity. An identical resync returns null. A no-op delete (map === previous) returns null.
- class AppConfigs: one per class of applications (DatasetDefinition, DatasetMetadata). State: wanted (array of app UUIDs in the order the member Set iterates, or null), apps (Map app -> AppMap), grouped (IMap<object, IMap<app, config>>, the shape _build_apps_configs emits today), pending (Set of object UUIDs, or the marker ALL). apply({ set, added, removed }) updates wanted, drops the AppMap of each removed app, creates one for each added app, and sets pending to ALL, because the app order decides the JSON key order of every inner map. A wanted-set change is rare, so O(N) is accepted there. apply({ key: app, value: change }) feeds that app's AppMap and adds its changed objects to pending. Readiness: nothing is returned until the wanted set is known and every wanted app has delivered a snapshot; an empty wanted set returns an empty map. When ready, each pending object's inner map is rebuilt from the wanted apps in wanted order (at most six gets), so body.metadata keeps the key order of today's full regroup. Returns { map: grouped, changed: Set | null } or null when nothing differs. changed is null on the first result and after a wanted-set change.

2. DATASET INDEX. DA/lib/dataset-index.js (pure).
- class DatasetIndex. Public persistent maps: entries (IMap<uuid, { structure, config, from, to }>, the `datasets` value), valid, invalid, defaults (IMap<dataset uuid, device uuid>, from default_dataset_device on the resolved entry). Private: windows (Map<uuid, { from, to } | null>, the resolve cache kept across changes), refs (Map<uuid, Set<uuid>>), referrers (Map<target uuid, Set<referrer uuid>>, keyed by the target even when it does not exist, so a dangling reference heals when its target appears), stats { applies, resolved }.
- apply(grouped, changed) returns { datasets, valid, invalid, defaults, changed } or null. Steps: update refs and referrers for each changed id from its single definition in grouped (no refs when it has zero or several definitions); take the transitive closure of the changed ids over referrers; delete those ids from windows; resolve each id in the closure with the memoised resolve, which reads every other dataset from windows; build the entry; replace the old entry only when structure, config (identity, then json_equal) or from/to (getTime, NaN equal to NaN) differ. changed == null means every key. The first apply always returns a value, even for an empty site. Why the cache is sound: today's resolver marks a dataset invalid by cycle only when the dataset is its own ancestor (visited is copied per child, dataflow.js:526, 609), so a result never depends on evaluation order, and a dataset outside the closure cannot depend on a changed one.
- resolve_window(structure, config, lookup) holds the per-kind rules moved verbatim from dataflow.js:518-673: session takes maxDate of its own from and the source from and minDate of the to values; union takes the earliest non-null from and the latest non-null to and ignores components with no window; the four device kinds give { from: null, to: null }; unknown structure, duplicate definitions, a missing or invalid reference and any path to a cycle give null. Dates are built with new Date(...). One addition: each resolve call is wrapped in try/catch and gives null, so a malformed config makes that dataset, and the datasets that refer to it, invalid.
- dataset_refs(structure, config): config.source when it is a string for Session limits, each string entry for Union components, else nothing.
- No bookkeeping field ever goes on an entry. The invalid entry is always exactly { structure: Constants.Special.InvalidDataset, config: null, from: null, to: null }.

3. DATAFLOW STREAMS. DA/lib/dataflow.js.
- _watch_apps(klass): cdb.watch_members(klass).pipe(watch_each(app => cdb.search_app_changes(app))).
- _build_app_changes(klass): rx.defer(() => fold of a new AppConfigs over _watch_apps(klass)), null results filtered out, rxu.shareLatest().
- changes: rx.defer(() => fold of a new DatasetIndex over _build_app_changes(DatasetDefinition)), null filtered, shareLatest. Value: { datasets, valid, invalid, defaults, changed }.
- datasets, valid_datasets, invalid_datasets, default_devices: `changes` mapped to one field with distinctUntilChanged() on identity. They stay plain instance properties assigned in the constructor, because five tests assign them on Object.create(DataFlow.prototype). default_devices now emits an Immutable Map (today a native Map) and only when a default dataset changes, which removes the diamond. Both consumers work with either type: watch_allowed calls get, stale_names iterates entries. _build_default_devices() stays as a prototype method that derives a native Map from this.datasets (default_datasets.test.js:474 calls it); the constructor no longer uses it.
- info_changes: cdb.search_app_changes(UUIDs.App.Info) through one AppMap, shared. general_infos is its map. metadata_changes: a second AppConfigs over DatasetMetadata. metadata is its map. functional_changes: today's inversion (dataflow.js:254-270) followed by a per-member diff with imm.is that keeps the old IList for unchanged members and emits { map, changed }. functional_types is its map.
- run() subscribes to changes, info_changes, metadata_changes and functional_changes for the life of the process, each through rxu.retryBackoff(5000, log). stop() unsubscribes; bin/api.js calls it beside defaults.stop(). A source error still reaches clients as today (an HTTP read rejects, an open notify subscription gets 500), because shareLatest resets on error; the only addition is that DataFlow reconnects without waiting for a client. Reducers are created inside rx.defer, so a re-subscribe starts clean.
- A late subscriber to a shared change stream gets one replayed value. Every consumer treats its first value per source as "everything changed".

4. PERMISSIONS. DA/lib/dataflow.js. One rule, three forms. Nothing here changes an answer.
- watch_grant_state(principal, permission): root gives rx.of({ all: true }); otherwise auth.watch_acl_with_perm mapped to { all: targets.has(Null UUID), targets } with distinctUntilChanged (equal when both are `all`, or when same_set says the target Sets are equal). An ACL push that does not change this permission emits nothing.
- watch_granted(principal, permission): watch_grant_state mapped to today's predicate.
- watch_allowed_check(principal, permission): emits { ok(id, device), changed }. For READ_STRUCTURE the direct grant is EditDataset. For READ_STRUCTURE and DEVICE_PERMS, ok is direct(id) || (device != null && use_device(device)); for other permissions ok is direct(id). changed is null on the first value and when either `all` flips; otherwise it is the symmetric difference of the direct target Sets plus default_dataset_uuid(device) for each device in the symmetric difference of the UseDevice target Sets.
- watch_allowed(principal, permission): for a non-device permission it returns watch_granted as today; otherwise combineLatest([watch_allowed_check, this.default_devices]) mapped to id => ok(id, devices.get(id)). filter_allowed_datasets, select_dataset_uuids and the six allowed_* methods are not edited. APIv1.check_dataset_acl is not edited. No memo cache is added, so Object.create tests keep working.
- Known existing difference, kept and pinned: for a default dataset that is invalid in the map (for example it has a second structure entry), the lists give no device-derived right, and check_dataset_acl allows it through UseDevice because it reads the raw UNS device config. Neither side changes.

5. PARTS. DA/lib/parts-index.js (pure) and dataflow.js.
- DataFlow.dataset_parts(uuid): an Observable of the dataset's part Set, or null when uuid is not a Dataset member. It watches cdb.watch_members(Class.Dataset); only while uuid is a member (distinctUntilChanged on members.has(uuid), then switchMap) it combines the members with cdb.watch_subclasses(uuid) and gives subs.filter(x => members.has(x)); it ends with distinctUntilChanged(imm.is). This is today's value for one key (dataflow.js:229-236, 198-204). It opens at most one ConfigDB WATCH, and none for a UUID that is not a Dataset member.
- allowed_dataset_parts(uuid, principal, permission) keeps its signature and values: combineLatest([dataset_parts(uuid), watch_allowed]) mapped to parts.filter(ok), or [] for null.
- dataset_parts_changes(uuid): dataset_parts(uuid) shaped as { map, changed: Set([uuid]), parents } for one key, for the single-key metadata view.
- class PartsIndex, for the search view. State: members (native Set), raw (Map<member, ISet>, the raw subclass Set of each answered member), parents (Map<part, Set<member>>, built from the RAW sets, so it knows a part before that part is a Dataset member), map (IMap<member, ISet>, raw filtered to current members). apply({ set, added, removed }) touches only each added or removed member X and the datasets in parents.get(X); it never refilters the other entries. apply({ key: member, value: subs }) replaces that member's raw Set, relinks parents from the old and new Set, and recomputes that one entry. Each returns { map, changed, parents } or null.
- DataFlow.parts_changes: rx.defer(() => fold of a new PartsIndex over cdb.watch_members(Class.Dataset).pipe(watch_each(m => cdb.watch_subclasses(m), stats))), shared with shareLatest. A new member opens one WATCH and re-subscribes none. It is subscribed only while a metadata SEARCH is open, as `parts` is today, so the ConfigDB load profile does not change. this.parts is parts_changes mapped to map. DataFlow no longer calls cdb.watch_members_subclasses.

6. NOTIFY. DA/lib/dataset-view.js and DA/lib/notify.js.
- class DatasetView, one per subscription. Options: sources (tag -> Observable; tags data, check, info, meta, ftypes, parts), required (array of tags), candidates(state) or a fixed key list, body(state, uuid). State: latest value per tag, children (Map<uuid, body>), ready (a Promise resolved by the first build), stats { computed, sent }.
- Start: the view subscribes to every source and only stores values during that synchronous phase. At the end of the phase it builds if every required tag has a value; otherwise it builds on the event that completes the required set. A source that is not required and has no value counts as empty. Because run() keeps the sources hot, the first build normally has every value.
- After the first build an event dirties keys: data -> its changed Set plus parents.get(id) for each id (all keys when null); check -> its changed Set plus parents.get(id) (all when null); info, meta, ftypes, parts -> their changed Sets (all when null). A dirty key is looked at only if it is a candidate or a current child. For each one the view computes body, compares with the held body by json_equal, and reports created, changed or removed.
- Any source error, required or not, errors the view. The session turns that into a 500, as today (notify.js:129-144 errors the subscription when the parts stream errors).
- Readiness per endpoint, equal to today's gates: metadata SEARCH requires data and check (today: the UUID list from the dataset map and the ACL; every other input has startWith(IMap()), notify.js:106-136). Structure SEARCH, WATCH v2/structure/:uuid and the four lists require data and check. WATCH v2/metadata/:uuid requires nothing.
- metadata_body(state, uuid): undefined unless the dataset is in data.valid and check.ok(uuid, defaults.get(uuid)); otherwise { uuid, name: info?.name ?? "UNKNOWN", from, to, function, metadata, parts } in today's key order with today's value types (notify.js:154-162). parts is the dataset's part Set filtered with the same ok rule and no validity check, or [] while unknown. structure_body(state, uuid, valid_only): the entry minus from and to.
- search_source(view) returns { full, updates, acl: rx.pipe() }. updates starts the view on subscribe and stops it on unsubscribe. full() awaits view.ready and returns { children: { uuid: { status: 200, body } }, response: { status: 204 } } from the current children in one synchronous run. SearchFilter.build_search calls full() before it subscribes to updates (W/lib/js-service-api/lib/notify-v2.js:77-86), so full() only awaits; it does not start the view. Changes before the snapshot are in it and are not sent. Changes after the snapshot go into an array until the next setImmediate, then go out in order, and after that go straight out. By then the snapshot has left with_full's concatMap, so nothing ever queues behind it, whatever the timing. Stopping the view clears the timer. Child updates keep today's shapes: { status: 200, child, response: { status: 201, body } } newly visible, { status: 200, child, response: { status: 200, body } } changed, { status: 200, child, response: { status: 404 } } removed.
- Handlers. metadata_search: view over data.valid with check(ReadDataset), parts from parts_changes. structure_search: view over data.datasets with check(READ_STRUCTURE); an invalid dataset the principal may read is a child with body { structure: InvalidDataset, config: null }. metadata_uuid: a one-key view with parts from dataset_parts_changes(uuid); at the end of the subscribe phase it sends { status: 200, response: { status: 200, body } } with the body it can compute then, or with no body, and afterwards sends on every body change, including back to no body. So a cold service and a principal that Auth does not know both get the bodyless 200 at once, as today. structure_uuid: a one-key view over data.valid; it sends only when a body exists and differs from the last body sent, and nothing when the dataset disappears, as today. The four lists: a membership-only view; each sends { status: 200, response: { status: 200, body: [uuid, ...] } } on its first build and when membership changes. A malformed uuid on a single WATCH still throws from the handler, which closes the WebSocket, as today.
- Deleted: _build_search_source, _metadata_resource_state, _structure_resource_state, the deep-equal import (and the dependency; DA has no lockfile and nothing else imports it), the unused express import.

7. MAKER. DA/lib/default-datasets.js.
- inputs() is the combineLatest that jobs() builds today, with a tap that stores this.latest before the debounce. jobs() keeps its output and its tests. run() pipes jobs() through coalesce(() => this.drain()) and rxu.retryBackoff(5000, log).
- drain() waits for a running pass, returns 0 if the maker is stopped or has no inputs, then runs make_all(missing_defaults(...)) from this.latest and records the pass promise in this.draining until it settles. The guard is in the class because coalesce errors its subscriber while its call still runs; after the retry delay a second coalesce would otherwise start a second pass beside the first. A list emitted earlier is only a trigger.
- make_all(missing, now) runs items through p-limit (already a dependency) with a new option concurrency, default 4. Per item: stop if this.stopped; t = now ?? this.clock(); skip a dataset made less than settle ago; skip a dataset that this.latest.datasets already has; await make(); stamp made with now ?? this.clock(). An explicit `now` still wins, which keeps the two pinned settle tests valid. The summary log line gains the pass duration.
- stop() sets this.stopped before it unsubscribes, so queued items make no ConfigDB call. run() clears it.
- renames() gets the same treatment: a tap stores this.latest_names, and run() pipes it through coalesce(() => this.rename_drain()) with the same one-pass guard and retry. make(), ensure(), rename_all(), the existing constructor options and the exports do not change. default_dataset_uuid is memoised per device in a bounded module Map.

ACCEPTED RESIDUAL COSTS (named in the PR and counted by tests, so they stay visible)
- The Dataset member list: ConfigDB sends the whole list per member change. The library parses it, builds an Immutable Set and compares it (once per process, shared by cacheSeq); watch_each then makes one native pass. O(N) per dataset made, about 0.4 ms at N=713.
- A list WATCH body: the whole UUID list per membership change, by wire contract. O(N) per list subscriber per dataset made, about 0.02 ms at N=713.
- An ACL push: Auth sends the whole ACL and auth.watch_acl_with_perm filters it once per subscriber. O(ACL size x that principal's open permission watches) per push. After the Set comparison the work is O(changed targets).
- A snapshot at subscribe and a wildcard grant gained or lost: O(N), once.
- A functional group change: the inversion and its diff are O(datasets that have a function). Default datasets have none, so this is off the burst path.
- A change to the set of structure or metadata applications: O(N), rare.
- api-v1.js: one O(N) permission filter per single-dataset read. No work per change.

WHY THIS STRUCTURE
- Per-subscription views, not views shared per principal. A subscription pays O(changed keys) either way, and a per-subscription view cannot show one principal another's data through a cache-key mistake.
- api-v1.js is not edited. Its reads are replays plus at most one O(N) filter per request and no work per change. Not editing it keeps HTTP risk at zero and keeps about ten test fakes untouched.
- Errors propagate as today. I rejected per-source retry inside the shared streams, because it would silently serve stale state where clients get a 500 today.
- parts is not held hot by run(), to avoid a new permanent WATCH per dataset on ConfigDB.

## Invariants

- HTTP API: no route, status code or body changes. DA/lib/api-v1.js is not edited in any stage. A request before the first snapshot still waits; it never gets a 404 or an empty list.
- Dataset map entries stay exactly { structure, config, from, to } with that key order. Valid entries carry the stored config object and Date or null for from and to. Invalid entries are exactly { structure: Constants.Special.InvalidDataset, config: null, from: null, to: null }. No extra field is ever stored on an entry.
- from and to are built with new Date(...), so clients receive ISO strings with milliseconds.
- Validity and window rules do not change: more than one structure-app entry, an unknown structure app, a reference to a missing or invalid dataset, or any path to a cycle makes a dataset invalid; a session takes the later from and the earlier to; a union takes the earliest non-null from and the latest non-null to and ignores components with no window; an object with no structure-app entry is not in the map.

## Risks

- The incremental index drifts from a full rebuild in a corner case: a cycle that forms or breaks, a dangling reference whose target appears, or a duplicate definition that comes and goes. Mitigation: The reverse index is keyed by the referenced UUID even when the target is missing. The S3 oracle compares the index with a verbatim copy of today's resolver after every one of 40,000 random changes, and the S1 goldens compare every public stream on a scripted site.
- Readiness of the dataset map. If the index emits before every structure app has answered, clients get a partial first list and the maker sees datasets as missing and makes them. Mitigation: AppConfigs returns nothing until the wanted set is known and every wanted app has a snapshot, and holds again while a newly added app has not answered. watch_each emits the set event before it subscribes a new member by construction. S3 and S4 test this with a delayed app, with a synchronous rx.of source and with a live Subject.
- Readiness of notify views. A view that waits for more sources than today removes an answer clients get today; a view that waits for fewer sends bodies with missing names when the sources are warm. Mitigation: Each view requires exactly what today's code gates on, and non-required sources count as empty. The view stores replayed values during its subscribe phase and builds once at the end of it, so a warm service sends settled bodies. R1 to R3 are captured on today's code in S1 and must pass unchanged in S6.
- A late subscriber to a shared change stream receives one replayed value whose changed Set describes an older change. Mitigation: Every consumer (the DataFlow folds, DatasetView, PartsIndex) treats its first value per source as a full snapshot. S6 tests a late subscriber on each source.
- A view emits a child update before the snapshot is taken and the snapshot does not hold it, or updates queue behind the snapshot and the stack overflow returns. Mitigation: full() takes the snapshot from the same held Map in one synchronous run. Updates after it are held in an array until the next setImmediate and then sent in order, so with_full's concatMap is idle when they arrive. S6 injects a change between subscribe and full(), injects 2,000 changes in the handoff window, and runs 2,000 children at subscribe and 2,000 updates after a wildcard grant.
- A missed invalidation leaves a stale metadata body. A body depends on the entry, the name, functional types, metadata, the parts Set, each part's Dataset membership and the permission on each part. Mitigation: One written dirty rule in DatasetView, with parents built from raw subclass Sets. The S6 oracle compares every view with a from-scratch computation after random event sequences that include permission changes on a part and a part that becomes a Dataset member.
- Permission drift between lists, views and single checks, or a builder who 'fixes' the invalid default dataset difference in either direction. Mitigation: One rule in watch_allowed_check, with watch_allowed built on it and APIv1.check_dataset_acl untouched. The S5 table asserts agreement where the code agrees today and pins the one named difference with today's answers on both sides. S5 states that no test may be made to pass by changing either side.
- The maker runs two passes at once after an input error, or keeps writing after stop(). Mitigation: The one-pass guard and the stopped flag live in the class, not only in the operator. S2 tests an input error during a pass that outlasts the retry delay, and stop() in the middle of a pass.
- The goldens are captured from the old code once and cannot be re-captured later. The old code cannot produce a structure search snapshot with an invalid dataset visible, its searches break at a few hundred children, and its message order and transient messages differ. Mitigation: Scenarios use about 60 datasets and compare reduced client state with every unspecified order sorted. ## As built: where the code differs from this plan

The seven stages are built. This section records each place where the code differs from the text above, and each plan fact that the code showed to be wrong. The text above is corrected in place only where it stated a wrong fact.

Stage 1
- The fake site now mirrors the library in three more ways than the stage 1 text lists. (1) The recipients of a change are fixed when the change is made, so a notify lag never sends a subscriber a change older than its snapshot. (2) Each SEARCH subscriber gets config bodies of its own, as a client that parses its own JSON does. (3) A class relation WATCH with no subscriber is dropped after 5 s, as cacheSeq drops it, and site.open_watches() counts the subscriptions callers hold, so a leaked member or subclass watch shows at once. Items 1 and 2 were built in stage 7, item 3 after it.
- Determinism: all three golden files record both scenarios twice. The notify golden recorded scenario B once while the old handlers took ten seconds a scenario.
- Vitest writes a missing snapshot and passes when CI is not set. Each golden file now compares the snapshot names in its committed file with the names its tests ask for, so a renamed step or describe block fails. The shape catalogue test makes its own recordings, so it can run alone.
- counters.grant_has counts every has() call on a grant Set. An ACL push costs one call for the Null UUID and up to three for each target, for each open permission watch, before any dataset is checked. A test in scale_baseline.test.js pins this.
- The suite takes about 7 s on Node 24. It took about 30 s while the old notify handlers ran the scenarios.

Stage 2
- D3 in scale_baseline.test.js changed by more than the flip. The maker in that test has concurrency 1, and its title and comment were rewritten. Four at a time would finish 40 datasets in 25 s, which is shorter than the settle time, so the test would no longer cover a pass that outlasts it.
- rename_all() did change. It stops at stop(): the name being set is finished, and no ConfigDB call is made for the rest of its list. The invariant "no ConfigDB call for a queued item after stop()" now holds for both passes.
- A pass ends for good at stop(). The maker counts its stops, and a pass that sees a new count makes no further item, so run() straight after stop() cannot wake the old pass. The new run's pass starts when the old one has ended.
- default_dataset_uuid keeps an answer only for a string as long as a UUID. A stored UNS device config can name any string as its device.

Stage 3
- watch_each turns every failure while it handles a Set into an error on its output: a value that is no Set, a factory that throws, and an inner sequence that throws when it is unsubscribed. It also starts no inner sequence when the consumer unsubscribes while it handles a Set value that a replaying upstream gave inside subscribe.
- DatasetIndex follows references with a loop, not recursion. The recursive form ran out of stack at about 2,550 datasets deep on Node 24, where the old whole-map code reached about 7,540. The loop has no limit. A RangeError can now come only from a union with too many components to take the earliest and latest of in one call; it still leaves apply(), as the plan's narrowed rule says.
- A dataset whose inner map is present and empty gets the invalid entry, as the old resolver gave it. The design text says a dataset with zero definitions has no refs and is not in the map. AppConfigs never emits an empty inner map, so the pipeline cannot reach this case.

Stage 4
- _build_changes reads the structure entries through an unshared sequence. Two shared sequences, one over the other, kept the six ConfigDB searches open for 2 s after the last reader when run() was not called, and a reader who came between 1 s and 2 s opened a second set.
- DataFlow has a public property `index`, the DatasetIndex of the current connection, which tests read for stats.resolved. `running` is declared in the constructor. _build_metadata, _build_general_info and _build_functional_types were removed with the three builders the plan names; nothing referenced them.
- Emission order. The dataset lists of DataFlow (allowed_valid_datasets and the other five) take the dataset map before the default devices. When a default dataset is pointed at another device, they emit once with the new config under the old right and then again without the dataset. Only api-v1.js reads them now, and it takes the newest value of each, so no client can see the first emission. The notify views read both maps as one value. A test through the real notify handlers pins that a principal with only UseDevice on the old device gets no message with the new config.
- "A name or metadata change re-resolves 0" (P1) is asserted in dataflow_incremental.test.js, because names and metadata never reach the index.

Stage 5
- The parts of a dataset are a set. PartsIndex keeps the Set it holds when a new subclass list gives the same parts in another order, and dataset_parts does the same through distinctUntilChanged. The old formula built every entry again and so gave the new order. A long-lived search, a single watch and a fresh reader can hold the same parts in different orders.
- While a new Dataset member has not answered, PartsIndex emits nothing. The old `parts` stream emitted the old subclass map filtered with the new member Set in that time, so a parent could show a new part before the part's own entry existed. The settled state is the same.
- The pinned permission difference has its before and after in the tree: reference_watch_allowed in tests/support/reference-datasets.js is the list predicate copied from the code before the keyed check, and allowed_check.test.js compares it with the new predicate for every principal, permission and dataset of the fixture.

Stage 6
- Three additions to production code: the export member_body, the DataAccessNotify.views registry, and the name, principal and registry options of DatasetView. The registry lets a test find the view of a subscription and shows that a closed subscription leaves none behind.
- The oracle in dataset_view.test.js checks body content too. It works every body out from the site's stored state with the whole-map reference code and the permission rule written out again, and compares that with what each view holds.

Stage 7
- Stage 7 also changed tests/support/fake-site.js and tests/current/scale_baseline.test.js, which are not in its file list, for items 1 and 2 under stage 1 above.
- The burst test runs the plan's site and smaller ones, with and without a notify lag. The blocked-time limits are checked only without a lag, and they catch only a large regression. They are 500 ms for the longest block and 20 s for the total, not the 50 ms and 2 s of S7: the test reads the real clock, and the smaller limits failed twice while the machine ran other suites. The measured values are about 0.7 ms and 0.44 s. The old handlers blocked for 2.9 s per dataset with one session, so they pass neither limit. The exact counts are the proof.
- docs/services/data-access.md said in two places that GET v1/structure/:uuid omits `config` for an invalid dataset and returns a `uuid` property. The route returns { structure, config } with config null. The docs now say so.
- The PR text is a draft outside the repository until the branch is pushed.

After the reviews
- The maker has its own retry, `backoff` in lib/rx-util.js, in place of rxu.retryBackoff. The waits are the same (5 s, doubling to 320 s). The shared retry goes back to 5 s only when a value comes out of the retried pipeline, and the maker's pipelines say nothing while no dataset is missing and no name is stale, so every input error counted as one more in a row for the life of the process. The maker now puts the wait back when the inputs have answered and stayed up for the debounce, and at run(). DataFlow.run() still uses rxu.retryBackoff: its sequences give a value whenever their source answers.
- drain() and rename_drain() note the count of stops when they are called. A call that waited for a running pass starts nothing if the maker was stopped in that time, even when run() has been called since. Before, such a call started a pass for the stopped subscription, ahead of the new run's own. It can wait only after an input error and a retry.
- The deep-chain test compares the index with the whole-map code at a fixed depth of 1,500. The depth the whole-map code can follow is not one number: five measurements in one process gave between 3,500 and 11,000 on Node 20 and between 5,000 and 11,000 on Node 24, so the 7,540 under stage 3 and the 7,500 in the client-visible list are single readings. A test that looked for the depth and then used nine tenths of it failed about one run in ten.
